# Запись траекторий с камерными ногами

Как записать эпизоды Quest с ногами от RGB-D камеры для датасета camera-legs
(дообучение политики на реальных движениях ног, push-T) и подготовить их к
обучению. Обычной записи для датасета нужны только эпизоды со шлема и лог
сервера. RGB-D кадры и AprilTag-метки нужны только для отдельных контрольных
сессий (проверка очистки ног, см. конец).

## 1. Перед сессией

**Камера.** D435i на штативе, 2.5–3.5 м до зоны, где стоит оператор. Шум
глубины растёт как квадрат расстояния: дальше 3.5 м ноги заметно дрожат. В
кадре всё тело оператора вместе со стопами при любом шаге. В кадре только
оператор: при втором человеке сервер не выбирает, кого вести, и ноги
временно переходят на Meta. **Не двигайте камеру во время сессии.**
Регистрация камеры сохраняется в шлеме на место камеры, а не на сессию.

**Сеть.** Остановки Wi-Fi на 1–5 с — главная причина потери камерных ног
(ep7, ep8, ep11). Подключите ноутбук к роутеру кабелем, шлем — к 5 ГГц той же
сети. В ep12 (2026-10-14, кабель) за 25 эпизодов не было ни одного провала
дольше 0.5 с, и камерные ноги работали 96–100% времени. Без кабеля не
записывайте.

**Ноутбук.**

```bash
uname -r      # должно быть 6.8.0-146-generic: только на нём работает GPU
ip -4 addr    # IP ноутбука в сети шлема (кабель: enp4s0, Wi-Fi: wlp3s0)
```

На ядре 138 YOLO идёт на CPU примерно на 6 Гц вместо 12–15. Перезагрузитесь
и выберите 146 в GRUB.

**Адрес сервера в шлеме.** Приложение читает его при запуске из
`files/g1/camera_stream_url.txt`. Если IP ноутбука изменился, проверьте и
поменяйте адрес (шлем по USB или `adb connect IP_ШЛЕМА:5555`):

```bash
P=org.g1lab.quest.smooth
adb shell run-as $P cat files/g1/camera_stream_url.txt
adb shell "run-as $P sh -c 'echo ws://IP_НОУТБУКА:8765 > files/g1/camera_stream_url.txt'"
```

Затем перезапустите приложение. Переустановка APK этот файл не затирает.

## 2. Запуск сервера

```bash
cd ~/programming/FURRY/skeleton
.venv/bin/python pose_yolo.py s --ws --log recordings/$(date +%F-%H%M).jsonl
```

Что проверить в выводе:

- строка бекенда: `torch-cuda`;
- `session_id ...` — запишите его вместе с заметками о сессии;
- раз в секунду `[тайминг]`: `age` около 50 мс, `не узнан:0`. Если
  `не узнан` всё время больше нуля, в кадре есть посторонний.

Сервер работает всю сессию. Лог `recordings/*.jsonl` нужен для разбора
проблем со связью.

## 3. В шлеме

**Настройки**, как в ep11:

- приложение `org.g1lab.quest.smooth`;
- политика `quest-111586-300`;
- Вид → `Ноги: Камера`;
- вид **наблюдателя**, не первое лицо. Левый стик переключает вид, и его
  легко задеть. Банк команд Meta для обучения собран с выключенным camera
  tracking, а в виде от первого лица GMR добавляет задачу HMD. Ноги от этого
  почти не меняются (p95 < 1.5°), но команда скорости корня меняется заметно
  (p95 vx 0.08, vy 0.14 м/с). В ep12 30 из 31 эпизода записаны от первого
  лица. Они годны, но расходятся с банком Meta. После первого эпизода
  проверьте `view` в `session_config.json` (команда в §4);
- сцена Push-T для толчков и ударов, «Пустая» для шагов и стойки.

**Регистрация.** Статусная строка должна стать зелёной: `Ноги: камера (обе)`.

- Если камера стоит на том же месте, сохранённая регистрация подхватится
  за 2–4 с.
- Если камеру передвигали, или висит красная `Ноги: Meta. Калибровка N%: …`: Вид →
  RGB-D → `Калибровать`. Затем ~30 с ходите лицом к камере (вперёд-назад и
  вбок на ~0.5 м), пока строка не станет зелёной.

**Проверка тела Meta.** Встаньте прямо, нажмите A, запустите симуляцию. Если
робот приседает или падает за первые секунды, хотя вы стоите ровно,
перезапустите приложение. Так было в ep10: Meta сообщала присед стоя, все три
эпизода непригодны. Пробные эпизоды до перезапуска записывать не нужно: в ep12
единственный такой эпизод был пригоден на 49% против 96–99% после
перезапуска.

**Запись эпизода.**

1. Встаньте прямо лицом к камере, A — калибровка.
2. Y — начать запись.
3. Первые 5 с стойте спокойно: обе стопы на полу, лицом к камере.
4. Движения (см. ниже) 1–2 минуты. Короткие эпизоды лучше длинных: при
   падении теряется меньше. Но не короче 30 с: в ep12 шесть эпизодов по
   1–15 с (случайные нажатия Y) почти ничего не дали.
5. Последние 5 с снова стойте спокойно.
6. Y — сохранить. После падения X сохраняет эпизод и сбрасывает робота.
   Эпизоды с падением оставляйте: цель от человека остаётся корректной, а
   провалы политики как раз нужны для дообучения.

Спокойная стойка в начале и в конце нужна для очистки: по ней оценивается
смещение голени камеры за сессию. В ep12 в 9 из 25 эпизодов не было ни
одной секунды тихой стойки, и почти все кадры для оценки пришли из первой
половины сессии.

**Что делать в эпизоде.** Нужны реальные движения ног, которых нет у
генеративных ног Meta:

- толчки и удары T-коробки, поочерёдно левой и правой ногой;
- подъём каждой ноги, шаги вперёд, назад и вбок, приставные шаги, повороты
  на месте;
- спокойная стойка между движениями.

Держитесь в основном лицом к камере. Боком дальняя нога ошибается на
20–34 см.

**Во время записи** поглядывайте на статусную строку:

- красная `Ноги: Meta. Камера: нет свежих данных` — проблема сети;
- `Ноги: Meta. Камера не видит ноги` — вы вышли из кадра.

Короткие провалы отбрасываются при обработке. Если строка красная больше
половины эпизода, перезапишите его.

**Заметки.** Для каждого эпизода запишите время, что делали (стойка, push-T,
шаги), что пошло не так. Для валидации нужен хотя бы один целый эпизод,
который не пойдёт в обучение. Удобно записать за сессию один лишний: около
90 с, с толчками обеими ногами и без падения.

Робот не возвращается к оператору: ошибка корня копится между эпизодами
(в ep12 до 25 м). На датасет это не влияет, потому что цель берётся от
человека. Для удобства оператора в виде наблюдателя сбрасывайте робота
между эпизодами.

## 4. Скачать эпизоды со шлема

Сразу после сессии, **до перезапуска приложения**: `runtime_stats.csv`
перезаписывается при новом запуске (так в ep5 потерялась часть статистики).

```bash
cd ~/programming/FURRY/prototypes/quest_g1
P=org.g1lab.quest.smooth
D=outputs/camera_skeleton/ep/ep12    # следующий свободный номер
mkdir -p $D
adb devices              # шлем по USB и по Wi-Fi виден дважды: тогда adb -s СЕРИЙНЫЙ
DAY=$(date +%F)          # эпизоды сегодняшней сессии
adb exec-out run-as $P ls -l files/g1/recordings | awk -v d=$DAY '$6==d{print $8}' > $D/list.txt
for e in $(cat $D/list.txt); do
  adb exec-out run-as $P tar -C files/g1/recordings -cf - $e | tar -xf - -C $D
done
for f in runtime_stats.csv camera_registration.txt menu_settings.txt; do
  adb exec-out run-as $P cat files/g1/$f > $D/$f
done
ls $D/episode-*/complete.json    # у неполного эпизода этого файла нет
grep -ho '"view":"[a-z_]*"' $D/episode-*/session_config.json | sort | uniq -c
```

`runtime_stats.csv` шлема и `frames.csv` эпизода пишутся по одним часам
(`wall_s` = `receive_ns`/1e9). По ним видно, были ли камерные ноги включены
живьём в каждом эпизоде.

## 5. Обработка в клипы для обучения

Сборка реплея (один раз, после изменений в `android/native`):

```bash
cd ~/programming/FURRY/prototypes/quest_g1
T=outputs/camera_skeleton/targets; SP=.venv/lib/python3.12/site-packages
mkdir -p $T/lib
ln -sf $PWD/$SP/onnxruntime/capi/libonnxruntime.so.1.23.2 $T/lib/libonnxruntime.so.1
c++ -O2 -std=c++17 -Iandroid/native -I$SP/mujoco/include -Ivendor/onnxruntime-android/headers \
  training/camera_commands.cpp android/native/{gmr,meta_retarget,simulation,camera_fusion}.cpp \
  $SP/mujoco/libmujoco.so.3.3.7 $SP/onnxruntime/capi/libonnxruntime.so.1.23.2 \
  -Wl,-rpath,$PWD/$T/lib -Wl,-rpath,$PWD/$SP/mujoco -o $T/camera_commands
```

Для каждого эпизода нужны пять шагов:

1. пакеты;
2. живой реплей с регистрацией;
3. реплей с ногами Meta;
4. очистка (clean3) со смещением голени, общим на сессию;
5. реплей очищенной цели.

Эпизоды короче 10 с пропускайте: на них очистка падает (нет кадров стойки),
а клипов короче 2 с датасет всё равно не берёт.

```bash
EP=outputs/camera_skeleton/ep/ep12
IDS=$(for d in $EP/episode-*; do
  [ -f $d/complete.json ] && [ $(wc -l < $d/mimic.csv) -gt 1000 ] && echo ${d##*episode-}; done)
for e in $IDS; do d=$EP/episode-$e                       # шаги 1-3
  .venv/bin/python training/camera_packets.py $d/camera.jsonl $T/$e.packets.txt
  $T/camera_commands android/assets $d $T/$e.packets.txt $EP/camera_registration.txt $T/$e
  $T/camera_commands android/assets $d - - $T/$e.meta
done
P=$(for e in $IDS; do echo $T/$e; done)
.venv/bin/python training/camera_targets.py $T/${IDS%% *} /dev/null --session $P
#   -> "session shin bias deg [[LP, LR], [RP, RR]] from N quiet frames"
for e in $IDS; do d=$EP/episode-$e                       # шаги 4-5
  .venv/bin/python training/camera_targets.py $T/$e $T/$e.clean3.txt --shin LP LR RP RR
  $T/camera_commands android/assets $d - - $T/$e.clean3 $T/$e.clean3.txt
done
```

Реплей идёт 15–60 с на эпизод; сессия из 25 эпизодов обрабатывается около
25 минут. Тяжёлые процессы запускайте не больше двух параллельно (7 ГБ ОЗУ).

Смещение считается одно на сессию, пока камера стоит на месте. После
перестановки камеры (третья строка `camera_registration.txt` сдвинулась на
5–10 см и больше) считайте его заново: в ep12 правая голень давала +4.1°, а
после перестановки в ep13–ep15 −4.4°. Без
`--session`/`--shin` оно оценивается по каждому эпизоду отдельно. Так
считался dataset-v1, но в коротких и активных эпизодах такая оценка
недостоверна: в ep12 правая голень получала от −12 до +39°, и в одном эпизоде
цель сгибала колено на 35° сильнее, чем у оператора. Если в выводе меньше
~5000 кадров стойки, оценка ненадёжна, запишите это в заметки. Сравните
половины сессии (функция `session_bias` по первой и второй половине
эпизодов): в ep12 левая голень дала −6.6/−6.3°, правая 3.7/11.2°.

Живой реплей печатает `camera_leg_ticks`: это число тиков с камерными ногами.
Если оно намного меньше, чем было живьём по `runtime_stats.csv`, сохранённая
регистрация не подходит к этому эпизоду. Тогда повторите шаги 2–5,
передав `-` вместо `$EP/camera_registration.txt` (так было с ep5 и ep7).
Реплей начинает со стороны регистрации, сохранённой в конце сессии, и должен
сначала её подтвердить. Поэтому начало эпизода иногда теряется: в ep12 так
пропало 27 с одного эпизода, при этом ноги в шлеме работали. Датасет
отбрасывает такие тики сам.

**Проверка перед сборкой:**

```bash
cd training && ../.venv/bin/python camera_quality.py $IDS
```

Что смотреть:

- `usable` — доля тиков, которые пойдут в клипы. В ep12 было 0.96–0.99, в
  dataset-v1 0.66–0.85.
- `mism50` — расхождение ног live и реплея, должно быть меньше 1°.
- Эпизод с `usable` < 0.7 разберите по 5-секундным окнам: смотрите,
  включена ли камера в реплее и сходится ли колено цели с командой.

Датасет собирается заново из всех эпизодов: старые пары dataset-v1 плюс
новые. Валидация — целые эпизоды, по одному из разных сессий:

```bash
cd training
../.venv/bin/python camera_dataset.py ../outputs/camera_skeleton/dataset-v2 \
  --assets ../android/assets --mirror --validation 1791882756630195 <id новой валидации> \
  --pair ../outputs/camera_skeleton/ep/ep5/episode-1791807316112666:../$T/1791807316112666 \
         ...                                     # остальные пары
         ../$EP/episode-<id>:../$T/<id>          # новые эпизоды
```

Эпизоды с ударами собираются отдельным датасетом с
`--source quest-camera-kicks --stage-base 201`, чтобы в смеси у них была своя
доля (`author_dataset.py --quest-shares`); так собран dataset-v3-kicks
(`outputs/camera_skeleton/ep/ep15/build_dataset.sh`).
Точный список пар последней сборки — в `episode_stages` из `manifest.json`
опубликованного датасета. Дальше публикация в
`datasets/quest-camera-legs/<дата>/dataset-vN` через Git LFS и шаги смешивания
из `training/quest_contact_clearance/README.md` (раздел Camera-leg clips).

## Контрольная сессия с метками (не для каждой записи)

Нужна только чтобы заново проверить или настроить очистку ног. Последняя
проверка была 2026-10-14 на ep11.

- AprilTag на обуви: id 0 — левая, id 2 — правая.
- Камера ближе, ~2.5 м: на 3.2 м метки занимают всего 23–35 px.
- Эпизод не длиннее, чем запись RGB-D. RGB-D начинает писаться при
  подключении шлема.

```bash
cd ~/programming/FURRY/skeleton
S=recordings/$(date +%F-%H%M)
.venv/bin/python pose_yolo.py s --ws --log $S.jsonl --record-rgbd $S-rgbd --record-rgbd-seconds 400
```

Расход диска около 1.9 ГБ на 5 минут. Папка RGB-D должна быть новой.
