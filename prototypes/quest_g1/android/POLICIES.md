# Выбор политики на Quest

Вкладка **Политика** содержит авторские TWIST2 `20k` и `25k`, а также
ONNX-кандидатов, включённых в конкретную сборку. При первом запуске выбрана
`twist2-20k` — прежняя политика main из `twist2_1017_20k.onnx` на pinned TWIST2
`b06178f19a22f2138cbd31f60c6d494bc263f67d`. Выбор сохраняется по ID между
запусками, сохраняется при смене сцены и показан в коротком HUD. Каталог
показывается по четыре строки с кнопками перехода между страницами.

Нажатие на другую политику загружает и проверяет SHA256, контракт float32
`[1,1432] → [1,29]` и пробный вывод. Только после успешной проверки заменяется
ONNX session и сбрасываются физика, действия, история наблюдений и калибровка.
После выбора нажмите **A**, затем **Запустить**. Ошибка загрузки сохраняет
прежнюю политику и ставит сессию на паузу. Выбор заблокирован во время записи
и в режиме сбора только движений человека. Повторное нажатие на текущую
политику ничего не сбрасывает. Отсутствующий сохранённый ID при новой сборке
возвращает выбор к `20k`; ошибка загрузки сохранённого кандидата также
возвращает приложение к проверенной по SHA256 `20k`.

## Догоняние

На той же вкладке есть **Догоняние позиции и поворота**, включённое по
умолчанию. Оно работает с любой выбранной политикой и использует существующий
`CameraPoseServo`: добавляет ограниченную коррекцию скорости по расхождению
камеры робота с целью. От первого лица цель — HMD после калибровки, в режиме
наблюдателя — камера GMR-референса, как в сравнительном ролике с догонянием.
Дополнительная скорость ограничена 0.4 м/с, итоговая — 0.8 м/с; для поворота
пределы 0.8 и 1.2 рад/с. Физическое положение робота не перезаписывается. Перед коррекцией
кинематика камеры обновляется из текущего `qpos`, чтобы live и replay
использовали одно и то же состояние после интеграции MuJoCo.

Переключение сохраняет настройку и сбрасывает робота и калибровку; затем
нажмите **A** и **Запустить**. Во время записи и сбора только движений человека
переключатель заблокирован. В HUD включённый режим помечен «+ догоняние».
Наличие коррекции не подтверждает устойчивость походки.

## Добавить дообучение в APK

Экспортируйте actor вместе с его frozen normalization в ONNX. Контракт
тензоров совместим с существующим runtime: физика 1000 Гц, inference и история
100 Гц. Формальная совместимость ONNX не подтверждает качество походки.

Создайте локальный JSON-массив по образцу
[`config/policies.example.json`](config/policies.example.json):

```json
[
  {
    "id": "quest-111260-500",
    "title": "Quest: дообучение 500",
    "note": "Эксперимент: 09.10 / 111260",
    "path": "/absolute/path/checkpoint_000500.onnx",
    "sha256": "expected 64 lowercase hex characters"
  }
]
```

`sha256` необязателен; когда он указан, несовпадение останавливает сборку.
Относительный `path` разрешается от папки JSON. ID должен быть уникальным и
состоять из ASCII букв, цифр, `-` и `_` (до 80 символов). Короткие `title` и
`note` показываются пользователю. Сборка упаковывает конкретные версии весов;
она не подхватывает меняющийся `latest` с GPU при работе приложения.

```sh
G1_POLICY_CONFIG=/absolute/path/policies.json android/build_apk.sh
```

Без `G1_POLICY_CONFIG` в APK входят только две авторские политики.
Генерируются `policy_catalog.txt`, `policy_catalog.json`, `policy.onnx` (20k)
и `policy-<id>.onnx`. Веса, локальный конфиг и APK находятся в игнорируемых
outputs/assets/build; они не включаются в Git вместе с этим изменением.

## Запись и replay

Manifest эпизода содержит `policy_id`, `policy_title`, `policy_note`,
`policy_file`, `policy_sha256` и соответствующий digest в `sha256`.
Поля `catch_up` и `first_person` сохраняют коррекцию и начальный режим вида;
изменения вида воспроизводятся из событий `ego_world` / `observer_view`.
GMR replay применяет ту же коррекцию перед плавным включением команды.
Отсутствующие поля старых эпизодов означают выключенные режимы.
В эпизод копируются точные выбранные веса под именем `policy.onnx`
(примерно 3 МБ дополнительно на запись); они входят в ZIP-экспорт.
Replay сначала использует сохранённые веса, затем соответствующий файл
assets, и проверяет SHA256. Он не подменяет отсутствующего кандидата baseline.
Старые manifest без полей политики продолжают использовать `assets/policy.onnx`.
Replay по-прежнему начинается с записанного reset, а не с произвольной
середины без полного состояния истории.

## Проверки

```sh
python -m unittest tests.test_policy_assets tests.test_episode_manifest tests.test_menu_input_patch tests.test_scene_assets -v
c++ -std=c++17 -Wall -Wextra -Werror -Iandroid/native tests/check_quest_menu.cpp -o /tmp/check-quest-menu
/tmp/check-quest-menu
python scripts/check_policy_selection.py
python scripts/check_menu_replay.py
```

Последние две проверки требуют подготовленных `android/assets` и native
MuJoCo/ONNX headers. Они проверяют реальные упакованные политики,
сброс истории, сохранение прежней session после ошибки и точный replay
синтетических эпизодов. Успешные desktop checks и сборка APK не подтверждают
установку и визуальную приёмку на Quest.
