# Записи «Два предмета» с Quest для π_high

Оператор собрал эти данные 2026-10-15 в симуляции FURRY на Meta Quest 3, сцена
`bimanual`. Каждый эпизод хранится в исходном виде: физические состояния, команды,
позы камеры, архивная модель MuJoCo и использованные ONNX. Готовый HDF5 содержит
RGB с камеры робота. Это офлайн-рендер симуляции, **не видео экрана Quest и не
passthrough**.

Задача: поднять оранжевый предмет левой рукой, синий — правой, удержать оба над
лотками без контакта с руками (подъём ≥ 4,5 см, 0,5 с покоя). Лимит — 90 с.

## Состав

| Набор | Эпизоды | Содержание |
| --- | ---: | --- |
| `raw/` | 105 | 70 с outcome=1, 35 с outcome=0 |
| `rendered/bimanual69-no-shadow-causal.hdf5` | 69 | 62 train + 7 valid, 23 192 RGB-кадра (12,9 мин) |

- **Настройка.** Одна конфигурация во всех записях: π_low `homie-v2` (backend
  `groot_decoupled_v1`), catch-up включён, камера `robot_head_pan_tilt_v1`, модель
  сцены `14b2533a…`.
- **Длина демонстраций.** От 8,2 до 14,8 с, медиана 11,1 с. Кадры после первого
  успеха обрезаны.
- **Исключено из HDF5.** Одна запись с outcome=1 начинается уже после окончания
  задачи. 35 неуспешных попыток лежат в `raw/`, но в HDF5 не входят.
- **Неуспешные попытки.** В 7 не поднят ни один предмет. В 22 поднят только один.
  В 6 подняты оба, но не удержаны над лотками. Падений нет: робот сместился
  больше чем на 0,3 м только в одной попытке.
- **Однородность стратегии.** В 68 из 69 демонстраций первым поднимается синий
  (правый) предмет. Модель не увидит обратного порядка.
- **Валидация.** Это одна сессия записи, поэтому validation не является
  независимым тестом. Раскладки разные: 104 seed на 105 записей.

`manifest.json` перечисляет все 105 эпизодов:
- исходы, seed;
- причины исключения;
- split и `demo_N`;
- SHA256 всех 2100 исходных файлов и HDF5.

Хэши файлов совпадают с `sha256sum`, прочитанными на шлеме до переноса.
Служебные маркеры `.download-exported` в датасет не включены.

## Скачать и проверить

Команды выполняются **из корня FURRY**. Нужны Git LFS и Python 3.12.

```sh
git lfs install
git lfs pull --include='datasets/quest-bimanual/**' --exclude=''
python3.12 -m venv .venv
.venv/bin/python -m pip install -r datasets/quest-bimanual/2026-10-15/tools/requirements.txt
.venv/bin/python datasets/quest-bimanual/2026-10-15/tools/build.py verify
```

Проверка делает следующее:
- сверяет SHA256 всех исходных файлов и HDF5;
- заново выводит из сырых данных все действия, исходные индексы кадров,
  временную сетку и `previous_command`;
- проверяет, что train и valid не пересекаются.

С флагом `--render-check` она ещё раз рендерит первый, средний и последний кадр
каждого эпизода. Для headless Linux предварительно задайте `export MUJOCO_GL=egl`.
Рендер EGL может отличаться на 1 уровень яркости в отдельных пикселях, поэтому
допуск — ≤ 2 уровня на < 0,1 % пикселей. Фактически отличался один уровень у
0,0007 % пикселей.

Нужен MuJoCo **3.3.7**: на нём записаны архивные `learning-model.mjb`.
Код `prototypes/quest_g1/g1_sim` и рендерер из
`datasets/quest-cup/2026-10-15/tools` берутся из этого же репозитория.

## Повторно построить HDF5

```sh
MUJOCO_GL=egl .venv/bin/python datasets/quest-bimanual/2026-10-15/tools/build.py \
  build /tmp/bimanual69-rebuilt.hdf5
.venv/bin/python datasets/quest-bimanual/2026-10-15/tools/build.py verify /tmp/bimanual69-rebuilt.hdf5
```

Существующие файлы не перезаписываются. Отчёт пишется рядом с выходным файлом.
Сборка на ноутбуке занимает около 2,5 мин. Повторная сборка воспроизводит команды,
RGB и split. Бинарный SHA256 нового HDF5 может отличаться из-за метаданных
контейнера.

Камера та же, что в cup-датасете. Положение головы берётся из текущего
физического кадра, а yaw/pitch — из **предыдущего отсчёта 30 Гц**. Сначала кадр
рендерится в 640×360 без теней, затем Pillow bilinear уменьшает его до 224×224.
При оценке политики нужна та же камера.

## Формат обучающего файла

| Путь HDF5 | Тип / размер | Значение |
| --- | --- | --- |
| `data/demo_N/obs/agentview_image` | uint8, N×224×224×3 | RGB камеры, без теней, LZF |
| `data/demo_N/actions` | float32, N×39 | 35 reference + 2 Grip + 2 gaze |
| `data/demo_N/obs/previous_command` | float32, N×39 | Предыдущая команда; первая строка нулевая |
| `data/demo_N/source_frame_index` | N | Индекс кадра исходной записи |
| `data/demo_N/timestamps` | N | Сетка 30 Гц |
| `data/demo_N/source_sim_time` | N | Время выбранного исходного состояния |
| `mask/train`, `mask/valid` | 62 / 7 имён | Разделение целых эпизодов |

Для каждой точки сетки берётся последний исходный кадр не позже её времени.
Reference записан после catch-up, то есть в том виде, в каком его получил π_low.
В validation попадают эпизоды с наименьшими content identity, по правилу
экспортёра. `dataset-report.json` и `dataset-verification.json` относятся к
опубликованному HDF5 с SHA256
`abbb4efae95946f9a3889894f53076e590a4154eb88993123b36f9cc5d2c505b`.

Обучение базовой модели (`python -m g1_sim.visual_training <hdf5> <out.pt> --device cuda`)
проверяет только то, что данные читаются и лосс сходится. Готовность и корректный
рендер датасета не доказывают, что автономная политика решит задачу.

Общая инструкция для новых записей: [TRAINING_CAPTURE.md](../../../prototypes/quest_g1/android/TRAINING_CAPTURE.md).
