# Записи чашки с Quest и восстановление камеры

Новая отдельная сессия: [59 демонстраций HOMIE-v2](../2026-10-15-homie-v2/README.md),
16 042 RGB-кадра, все демонстрации в train.

Данные собраны оператором в симуляции FURRY на Meta Quest 3. Здесь сохранены
исходные попытки вместе с физическими состояниями, командами, позами камеры,
архивными моделями MuJoCo и использованными ONNX. Готовый HDF5 уже содержит RGB
камеры робота. Это офлайн-рендер симуляции, **не видео экрана Quest, passthrough
или внешней RGB-D камеры**.

## Состав

| Набор | Эпизоды | Содержание |
| --- | ---: | --- |
| `raw/`, scene `cup` | 51 | 48 с автоматическим outcome=1; 3 без успеха |
| `raw/`, scene `wb_dex` | 8 | 4 с outcome=1; 2 с outcome=2; 2 с outcome=0 |
| `rendered/cup44-no-shadow-causal.hdf5` | 44 | 40 train + 4 valid, 12 982 RGB-кадра |

Четыре записи cup с outcome=1 начинаются уже после окончания задачи и не входят
в 44 демонстрации. Остальные неуспешные попытки тоже сохранены в `raw/`, но не
выданы за успешные примеры. WB-Dex не смешан с обычной чашкой в готовом HDF5.
`manifest.json` перечисляет все 59 эпизодов, исходы, причины исключения,
принадлежность split, размеры и SHA256 всех 1180 исходных файлов и HDF5.
Исходные файлы сохранены побайтно; служебные локальные `.download-exported`
маркеры в датасет не включены.

Две совместимые версии сцены cup сохранены отдельными model families.
`training-manifest.json` фиксирует точный состав train/valid и идентичность
эпизодов. Это одна сессия; validation не является независимым тестом новых
операторов или раскладок. Meta lower-body tracking содержит оценённые положения
ног, а не измерения трекерами стоп.

## Скачать и проверить

Команды выполняются **из корня FURRY**. Нужны Git LFS и Python 3.12.

```sh
git lfs install
git lfs pull --include='datasets/quest-cup/**' --exclude=''
python3.12 -m venv .venv
.venv/bin/python -m pip install -r datasets/quest-cup/2026-10-15/tools/requirements.txt
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py verify
```

Проверка сверяет все файлы по SHA256, все команды и исходные индексы кадров,
временную привязку, предыдущую команду, непересечение split и декодирует весь
RGB-массив. Недокачанные LFS pointers не являются данными: сначала выполните
`git lfs pull`. MuJoCo **3.3.7** обязателен для архивных `learning-model.mjb`.
Установка TWIST2, Android SDK, Torch и загрузка модели на GPU для рендера не нужны.

## Получить MP4 из уже подготовленных RGB

Нужен `ffmpeg` в PATH. Эта команда только читает HDF5 и не требует OpenGL:

```sh
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py video \
  episode-1792014836827567 /tmp/cup-training-camera.mp4
```

Результат: 224×224, 30 fps, без звука. Это RGB, использованные для обучения;
H.264 является сжатием с потерями. Сам HDF5 хранит uint8 RGB с LZF без потерь.
Имена всех 44 доступных эпизодов перечислены в `training-manifest.json`.

## Восстановить исходный вид камеры из raw

Для любого из 59 эпизодов, включая неуспешные и WB-Dex:

```sh
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py video \
  episode-1792014854756726 /tmp/cup-recorded-camera.mp4 --recorded-gaze
```

Результат: 640×360, 30 fps. Команда загружает **модель из самого эпизода**,
восстанавливает `qpos/qvel`, mocap и userdata, выполняет `mj_forward`, затем
применяет сохранённые camera position/quaternion. Политика повторно не запускается,
новая физическая траектория не генерируется. Действующие исходы/успехи не меняются.
Невалидные кадры и интервалы паузы/разрыва пропускаются; отдельные непрерывные
участки соединяются. Поэтому это реконструкция сохранённого времени симуляции,
а не непрерывная запись реального времени. Тени отключены.

На macOS рендер запускается из обычной вошедшей графической сессии.
`invalid CoreGraphics connection` означает отсутствие доступа к ней, а не
повреждение датасета. Для headless Linux с настроенным GPU/EGL:

```sh
export MUJOCO_GL=egl
```

## Повторно построить обучающие RGB и HDF5

```sh
# Сначала один эпизод; исходный HDF5 не меняется.
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py rebuild \
  /tmp/cup-one.hdf5 --episode episode-1792014836827567

# Все 44 эпизода, прежнее разделение 40/4.
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py rebuild \
  /tmp/cup44-rebuilt.hdf5

# Проверить повторный рендер начала/середины/конца для каждой family/split.
.venv/bin/python datasets/quest-cup/2026-10-15/tools/camera_data.py verify --render-check
```

Существующие выходные файлы не перезаписываются. Для полного повторного экспорта
нужны примерно ещё 0,8 ГБ. Он воспроизводит массивы RGB/команд и split; бинарный
SHA256 нового HDF5 не обязан совпадать из-за различий метаданных контейнера.
Разные драйверы OpenGL могут дать небольшие различия пикселей; строгая проверка
`--render-check` рассчитана на одинаковое окружение рендера и сообщает расхождение.

Обучающий вариант намеренно отличается от `--recorded-gaze`: он использует
текущий физический head camera transform и **yaw/pitch предыдущего отсчёта 30 Гц**.
В первом кадре используется сохранённый начальный gaze. Это не даёт текущему,
ещё не предсказанному действию камеры попасть в observation. Сначала рендерится
640×360 без теней, затем изображение масштабируется Pillow bilinear до 224×224
без letterbox. При оценке политики нужен тот же вариант камеры.

## Формат обучающего файла

| Путь HDF5 | Тип / размер | Значение |
| --- | --- | --- |
| `data/demo_N/obs/agentview_image` | uint8, N×224×224×3 | RGB камеры, без теней |
| `data/demo_N/actions` | float32, N×39 | 35 reference + 2 Grip + 2 gaze |
| `data/demo_N/obs/previous_command` | float32, N×39 | Предыдущая команда; первая строка нулевая |
| `data/demo_N/source_frame_index` | N | Индекс кадра исходной записи |
| `data/demo_N/timestamps` | N | Сетка 30 Гц |
| `data/demo_N/source_sim_time` | N | Время выбранного исходного состояния |
| `mask/train`, `mask/valid` | 40 / 4 имён | Разделение целых эпизодов |

Выбирается последний исходный кадр не позже времени сетки. Текущие действия
хранятся как обучающая цель, предыдущие — как observation. Кадры после первого
успеха обрезаны. `dataset-report.json` и `dataset-verification.json` относятся
к уже готовому HDF5 с SHA256
`6f0cd24a85e68a9a5ca140418e7edf784e4f2cf43a8698afbb9ac39b0b9ccd39`.

Архивные ONNX лежат рядом с исходными эпизодами для provenance; при восстановлении
изображений они не исполняются. Git LFS хранит одинаковые модели одним объектом.
Наличие датасета и корректного рендера не доказывает успех автономной политики.

Общая инструкция новых записей: [TRAINING_CAPTURE.md](../../../prototypes/quest_g1/android/TRAINING_CAPTURE.md).
