## 1. Решение за одну минуту

**Да, метод применим к FURRY. Прямой перенос готового DexWeave сейчас недоступен, а результат «как у авторов» потребует нового контура данных, ретаргетинга и обучения.**

На момент проверки официальный репозиторий содержит README и два изображения. Код обещан, опубликованных releases и весов нет; файла LICENSE также нет. Проверенный commit — `98d79f4ea8f22887d30621946d7b240f5d0c0926`. Сейчас можно подготовить совместимые данные и реализовывать метод по статье; подтвердить совпадение с авторской реализацией удастся после её появления. [Проверенное дерево репозитория](https://github.com/WU-CVGL/DexWeave/tree/98d79f4ea8f22887d30621946d7b240f5d0c0926), [releases](https://github.com/WU-CVGL/DexWeave/releases).

Наши главные препятствия:

1. **Постановка задачи.** DexWeave обучает отдельную политику для заданной демонстрации. Произвольное живое телеуправление — дополнительная исследовательская задача. [Страница проекта](https://dexweave.github.io/).
2. **Управление захватом.** На текущем этапе используем запястья и Grip с заданной формой захвата; перенос независимой артикуляции человеческих пальцев отложен.
3. **Virtual legs.** Это основной вход для ног в обучении и исполнении. Требуется согласовать его с физически допустимой опорой робота.
4. **Интерфейс и модель робота.** Наш runtime жёстко привязан к TWIST2, а трёхпалые кисти отличаются от авторского робота.
5. **Взаимодействие с предметом.** Для манипуляции нужна согласованная демонстрация «тело с virtual legs + запястья/Grip + предмет»; текущих записей ходьбы достаточно для первичной проверки тела, но не полного навыка с предметом.

**Рекомендуемый первый результат:** физическое исполнение body-reference на основе существующих Quest-записей с virtual legs. После проверки тела — короткая манипуляция виртуальной чашкой с запястьями/Grip и заданной формой захвата, отдельная обученная политика и запуск на Quest. Онлайн-телеуправление оценивается отдельным этапом.

Все предложения ниже — инженерный план для FURRY. Новое обучение, установка APK и проверка устройства в рамках этого отчёта не выполнялись.

## 2. Что именно переносим

DexWeave связывает ретаргетинг взаимодействия с совместным управлением телом и кистями. Для нас ценна возможность согласовывать положение руки, форму захвата и предмет в одном процессе. На сайте показаны IsaacLab → MuJoCo и физический G1; это поддерживает выбор метода для нашего симулятора, но не подтверждает его скорость на Quest. [Метод и демонстрации](https://dexweave.github.io/).

Ключевые параметры из статьи, нужные для проектирования интерфейсов:

| Часть | Авторская постановка |
|---|---|
| Ретаргетинг | Инициализация тела/кистей, затем совместное уточнение рук, запястий, пальцев при сохранении нижней части тела |
| Опора | Ограничения положения опорных стоп выводятся из исходной кинематики ног |
| Робот | G1 + Inspire RH56DFQ; 41 действие: 29 тела + 12 независимых приводов кистей, с mimic-связями |
| Actor | 238 входов = 211 признаков робота + 27 объекта |
| Признаки робота | Reference q41/q̇29; история позиции reference-anchor21; ориентация6; angular velocity3; current q41/q̇29; previous action41 |
| Объект | Текущая/reference позы и покомпонентная разность; каждая поза — позиция3 + rotation6, в текущих осях torso |
| Архитектура | Анатомические токены; направленные маски attention; объект обусловливает верх тела |
| Обучение | Совместный PPO без pretrained tracker, teacher–student и residual refinement |
| Частоты | Физика 200 Гц, управление 50 Гц; 4096 сред |
| Время | История anchor охватывает 120 мс; future-lookahead в составе actor не заявлен |

Источник всей таблицы: [статья, §3 и приложения A–B](https://arxiv.org/html/2609.34724v1). Полный набор reward, PD, action scales, noise, termination и PPO settings следует брать непосредственно из приложений, фиксируя версию.

На сайте приведено **97,5%** для пяти референсов манипуляции в MuJoCo. Это доля прогонов, дошедших до конца reference/лимита времени; её нельзя переносить на наши cup success или точность управления оператором. [Таблица результатов](https://dexweave.github.io/).

## 4. Наши датчики: что они должны давать

**Датчики человека создают эталон движения. Фактическое состояние робота приходит из MuJoCo.** Это два разных потока: подставлять суставы Meta вместо текущих суставов робота в actor нельзя.

| Сигнал | Источник в нашем проекте | Необходимая доработка |
|---|---|---|
| Движение головы/рук оператора | HMD, Meta body, при выбранном режиме — контроллеры | Единые timestamp, frame, калибровка и регистрация пропусков |
| Команда захвата | Существующий Grip и позы запястий | Для манипуляции задать отображение Grip в позу пальцев робота |
| Движение ног | **Meta virtual legs — основной источник** | Согласовать reference с опорой и динамикой робота |
| Состояние робота | MuJoCo qpos/qvel и FK | Собрать признаки в системе координат новой политики |
| Текущий виртуальный предмет | MuJoCo freejoint/FK | Преобразовать в torso frame, выдержать порядок обновления |
| Желаемый предмет | Отдельная демонстрация взаимодействия | Записать синхронную reference-траекторию |

**Базой остаётся существующий формат эпизода.** Для воспроизведения используем сохранённые body-позы с virtual legs, HMD/controllers/Grip, timestamps, flags, версию скелета, калибровку, reference, фактическое состояние робота, политику и воздействия. В metadata достаточно зафиксировать источник ног `meta_virtual_legs` и версию обработки reference. Отдельная классификация каждого кадра по происхождению для этого этапа не нужна; пропуски отражаются существующими flags и временем.

Для этапа манипуляции добавляются только недостающие данные: согласованная reference-траектория предмета, идентификатор его модели и параметры отображения Grip в форму захвата. Фактическое состояние предмета и контакты берутся из симуляции и сохраняются для оценки.

**Существующие записи с virtual legs — основной материал для первого эксперимента с телом.** Сбор hand joints и смена режима ввода не являются условиями начала. Артикуляция отдельных пальцев остаётся возможным последующим расширением, когда потребуется воспроизводить полноценные dexterous-навыки.

## 5. Virtual legs как основа обучения и исполнения

**Virtual legs — штатный источник движения ног в целевой системе.** Обучение и исполнение должны использовать одинаковую обработку этого потока: frames, масштабы, частоты, задержки и правила построения reference. Чистый mocap полезен для проверки базовой реализации, но не заменяет оценку на наших Quest-записях.

Цель — физически устойчивые шаги робота, согласованные с движением таза и работой рук. Критериями служат движение, баланс и контакты робота в MuJoCo. Точное совпадение с невидимой реальной стопой человека в текущую приёмку не входит; внешняя камера может использоваться для дополнительной диагностики и не является обязательным источником ног.

Что необходимо сделать в адаптации FURRY:

1. **Сохранять исходную генерацию ног.** Не скрывать jumps, freezes и пропуски сглаживанием до записи. Разделять raw и исправленный reference.
2. **Строить согласованный reference.** Проверять длины сегментов, joint limits, высоту пола, непрерывность таза, положение стоп и достижимость поз. При исправлении reference сохранять связь с исходным потоком virtual legs.
3. **Оценивать интервалы опоры.** Скорость, высота и стабильность виртуальной стопы задают предполагаемую опору reference. Проверять её согласованность на последовательности и отдельно измерять фактические контакты робота при исполнении. Это разные величины.
4. **Не закреплять ошибочную опору жёстко.** При сомнительном интервале использовать отдельный режим обработки неопределённости; при противоречии помечать участок для проверки. Мягкие ограничения или восстановление опоры будут нашими изменениями метода и требуют собственной абляции.
5. **Развести качество reference и качество policy.** Сначала проверить кинематику стоп, затем свободное физическое исполнение с массой предмета и контактами. Чистая анимация не гарантирует устойчивости.

Пример ошибки: virtual legs показывают обе стопы неподвижными, а HMD требует движения вперёд. Если одновременно требовать буквального следования ногам и догоняния таза, цели могут стать несовместимыми. Новый reference должен разрешать это противоречие до оценки политики.

Имеющийся эксперимент с ослаблением tracking ног уменьшал часть trips, но ухудшал другие показатели. Поэтому решение «просто снизить вес ног» не подтверждено. [Завершённые абляции](</Users/vlad/Documents/ChatGPT/VR-телеуправление гуманоидом/outputs/quest-locomotion-ablations-20261010/RESULTS_20261012.md>).

**Критерий успеха адаптации:** политика устойчиво исполняет reference из virtual legs и сохраняет качество движения верхней части тела. Для манипуляции к этому добавляется физический успех задачи с предметом. Снижение ошибки следования виртуальным ногам само по себе недостаточно.

## 6. Кисти робота: текущий этап и полное расширение

**Для текущего этапа предлагается сохранить имеющиеся кисти и вход Grip.** Сначала проверяется тело; затем для манипуляции задаётся форма захвата и её изменение по Grip. Hand joints человека для этого не нужны. Управление отдельными пальцами через новую policy относится к последующему расширению.

Для полного переноса dexterous-компонента остаются два варианта:

| Вариант | Выигрыш | Цена и ограничения |
|---|---|---|
| **Симулировать авторский тип Inspire** | Уменьшаем различия embodiment при воспроизведении | Нужны точная модель, mimic-связи, инерции, ограничения, контакты и новый рендер/actuator mapping |
| **Оставить наши трёхпалые кисти** | Сохраняем текущую модель FURRY | Перестраиваем hand fitting, описатели контакта, выходы actor и обучаем под 14 приводов; некоторые движения пяти пальцев недоступны |

Для последующего максимально близкого воспроизведения авторской dexterous-постановки первый путь уменьшит различия модели. В рамках симуляции он не требует покупки физических кистей. Доступность корректных assets и условия их использования нужно проверить при выборе модели.

Если остаёмся на текущих кистях, это полноценная адаптация к другой морфологии. Нельзя получить её добавлением двух нулей к выходу политики. Требуется согласовать FK, контактные поверхности, joint limits, знаки приводов, torque limits, PD и динамику пальцев.

Для ограниченной задачи чашки допустим прототип с заданной формой захвата или grip-synergy. Это может проверить физическое взаимодействие и управление телом, но не демонстрирует перенос произвольной человеческой артикуляции.

Существующий assisted tennis Grip использует weld и фиксированную форму кисти. Он не подходит как подтверждение успешного физического dexterous grasp: соответствующие испытания новой политики должны проходить на свободном предмете, удерживаемом контактами. Текущий путь пальцев виден в [Simulation::Step](</Users/vlad/Documents/ChatGPT/VR-телеуправление гуманоидом/.tools/furry-publish/prototypes/quest_g1/android/native/simulation.cpp:158>).

## 7. Предметы, координаты и масштаб

### Виртуальная сцена — подходящая первая постановка

В MuJoCo текущее положение чашки известно точно. Для нашей симуляции это штатный источник обратной связи. Можно отдельно включать noise/delay для сопоставления с выбранной процедурой обучения. Внешняя камера объекта нужна только для сценария с реальным предметом либо специального эксперимента с визуальными наблюдениями.

Однако **текущее состояние объекта не заменяет желаемую траекторию**. Для текущего scope предлагается отдельный режим демонстрации: оператор двигает виртуальную чашку контроллером, Grip задаёт захват/отпускание, а запись сохраняет body с virtual legs, запястья, Grip и предмет. Затем строится robot reference с заданной формой захвата. Такой режим ещё предстоит реализовать; hand joints он не требует. Запись неуспешного захвата старым G1/TWIST2 не становится успешной демонстрацией автоматически.

Режим демонстрации может использовать прикрепление предмета к контроллеру, но последующий robot reference обязан пройти проверку достижимости и контактов, а физический rollout — удерживать предмет самостоятельно.

### Один согласованный мир

Нужно явно описать преобразования Quest STAGE → мир сцены → reference/robot torso, камеры → STAGE, controller/hand → анатомические маркеры. И отдельно — масштаб перемещения и морфологическую подгонку конечностей.

Если кисть масштабируется вокруг тела, а объект остаётся в прежнем месте, контакт теряется. Поэтому возле предмета оптимизация должна разрешать ошибку вдоль всей цепи руки, сохраняя цель взаимодействия и допустимые суставы. Простое масштабирование запястья по коэффициенту armScale этого не решает.

При изменении масштаба виртуальной сцены согласованно меняются reference тела, предмет, геометрия и отображение. Массу и инерцию предмета надо задавать явно для новой сцены. Реальный предмет физически масштабировать нельзя: для него требуется достижимая геометрия задачи.

## 8. Предлагаемая архитектура

```mermaid
flowchart TD
    Q[Quest: body с virtual legs, HMD, controllers, Grip] --> D[Существующий эпизод]
    O[Траектория предмета для этапа манипуляции] --> D
    D --> V[Калибровка, проверка данных и опоры]
    V --> R[Reference тела; для манипуляции — захват и предмет]
    R --> T[Обучение отдельной политики на GPU]
    T --> E[Экспорт и проверка ONNX]
    E --> P[Новая policy в Quest]
    R --> P
    M[Текущее состояние MuJoCo] --> P
    P --> A[Приводы тела]
    G[Grip и заданная форма захвата] --> H[Приводы пальцев]
    H --> M
    A --> M
```

Первая версия использует сохранённый reference. Запись и обучение могут выполняться на Mac/GPU-сервере, а исполнение остаётся автономно внутри Quest. Unity для этого не требуется.

Для live-версии блок сохранённого reference заменяется причинным генератором целей из текущих датчиков. Это отдельная работа: потребуются обучение на распределении живых команд, переходы между движениями, обработка потери трекинга и проверка новых, заранее не записанных траекторий. Отсутствие заявленного future-lookahead не доказывает такую генерализацию.

### Что менять в коде

Названия новых сущностей ниже — предложение интерфейсов, их пока нет в репозитории.

| Работа | Точка интеграции | Проверяемый результат |
|---|---|---|
| Metadata существующей записи | `recording.h`, manifest/replay | Фиксированы источник ног, версия обработки; body/HMD/controllers/Grip воспроизводятся |
| `InteractionReference` | Отдельный offline pipeline рядом с GMR | Reference из virtual legs; для манипуляции добавлены Grip-derived захват и объект |
| `PolicyBackend` / `PolicyContract` | `simulation.cpp`, policy manifest/menu | Тип политики определяет формы, normalization, cadence, frames, joints, action scales и PD |
| Новый observation builder | Доступ к MuJoCo и reference | Каждый компонент сверяется с эталонной Python-реализацией |
| Отображение Grip в захват | Существующий hand-control и модель сцены | Для манипуляции форма захвата достижима, контакты проверены; hand-policy отложена |
| Полная идентичность модели | Manifest/recording/replay | Сохраняются policy, model/geometry, normalization, reference и schema hashes |

Сейчас меню закономерно отвергнет новый несовместимый actor. Изменять только проверку shape недостаточно: надо заменить весь контракт наблюдений и воздействий. ## 9. Как сохранить подход авторов

Предлагаются два явно различимых результата:

- **Воспроизведение по статье:** авторская модель/постановка, фиксированный reference, описанные архитектура, reward, PPO, normalization, DR и termination. До выхода исходников остаются непроверенные детали реализации.
- **Адаптация FURRY:** тот же проверенный базис, но наши сенсорные данные, обработка virtual legs и, при выбранном варианте, наши кисти. Каждое изменение фиксируется и сравнивается с базисом.

**На текущем этапе выбран второй результат:** тело управляется по reference из virtual legs, пальцы — существующим Grip с заданной формой захвата. Это ограниченный перенос компонентов DexWeave. Полная авторская сеть из раздела 2 описывает целевую dexterous-постановку; её совместное управление телом и пальцами пока не воспроизводится. Для первого этапа с телом следует начать с body-only постановки; добавление объекта при внешнем Grip будет отдельной явно зафиксированной адаптацией.

Начать следует с эталонного качественного reference, чтобы проверить реализацию без ошибок нашего capture. Затем заменить данные на Quest. Если всё одновременно поменять на первом запуске, невозможно будет определить причину неудачи.

Существующий TWIST2 trainer полезен инфраструктурой запусков, логов и оценки. Его reward/observation/normalization нельзя автоматически считать подходящими новой постановке. Перенос TWIST2 checkpoint в новую сеть также требует самостоятельного обоснования.

**Не добавлять к «авторскому PPO» новые whole-run KL-stop и остановку обучения по validation regression.** Параметры оптимизации воспроизводятся из фиксированного источника, а решение о пригодности checkpoint принимается отдельно после оценки. Сохранять полные конфиги, seeds, actor/critic/optimizer и происхождение данных.

Непубликация кода оставляет неопределённость относительно точного поведения solver, экспорта и training/deployment glue. Поэтому обучение до релиза можно честно назвать реализацией по статье; обещать точную воспроизводимость авторского результата рано.

## 10. Поместится ли это в Quest

**Подтверждённого запрета нет; подтверждённой производительности тоже нет.** Формат сети сам по себе не доказывает ни достаточность, ни нехватку мобильного CPU.

Для первого прототипа тяжёлую подготовку reference и обучение следует выполнять вне шлема. Quest получает готовую последовательность и actor. Так вопрос производительности разделяется на измеряемые части.

Проверка исполнения должна охватывать:

- корректность экспорта PyTorch → ONNX и совпадение выходов на записанных наблюдениях;
- поддержку операторов установленным ONNX Runtime Android;
- время inference p50/p95/p99, пропущенные control deadlines, память и нагрев;
- MuJoCo с выбранной кистью и контактами, рендер обеих глаз, sustained RTF;
- задержку от изменения цели до физического движения, без смешивания её с временем inference.

При выбранном управлении 50 Гц период составляет 20 мс: это бюджет всего control цикла. Физику FURRY на 1 кГц не требуется автоматически переводить на частоту actor. Нужно отдельно проверить timestep, action hold, PD, дискретизацию reference и истории; различия между training physics и MuJoCo остаются предметом sim-to-sim оценки.

Catch-up в FURRY дополнительно изменяет команды после GMR. В первом воспроизведении новой политики его следует отключить и измерить tracking напрямую; затем сравнить отдельным условием, если он нужен продукту. Иначе это скрытая дополнительная переменная. [Место коррекции команд](</Users/vlad/Documents/ChatGPT/VR-телеуправление гуманоидом/.tools/furry-publish/prototypes/quest_g1/android/native/quest_runtime.cpp:698>).

## 11. Последовательность работ и критерии перехода

| Этап | Конкретный результат | Условие перехода |
|---|---|---|
| **0. Зафиксировать базис** | Body-only постановка, virtual legs, текущие кисти/Grip, policy contract и матрица отличий | Текущий scope не зависит от захвата hand joints |
| **1. Проверить существующие эпизоды** | Согласованные body/virtual legs, HMD/controllers/Grip | Времена, frames, калибровка и пропуски воспроизводятся |
| **2. Подготовить reference тела** | Допустимое движение G1 из текущих Quest-записей | Joint limits, опора и движение таза согласованы |
| **3. Проверить базовую реализацию** | Policy для качественного reference на desktop | Поведение и метрики воспроизводимы; сохранены полные конфиги |
| **4. Обучить на virtual legs** | Body-policy для наших Quest-reference | Устойчивость, движение и качество верхней части тела на отложенных прогонах |
| **5. Перенести исполнение на Quest** | ONNX + новый backend + артефакт reference | Численная parity, длительный runtime benchmark, живая проверка |
| **6. Добавить манипуляцию** | Согласованный reference запястий/Grip/предмета; сначала стоя, затем с шагами | Физический захват/перенос/отпускание вместе с устойчивостью |
| **7. Исследовать live teleop** | Работа на новых командах оператора | Независимые сессии, новые траектории и проверенные переходы/dropouts |

Этапы подготовки данных и базовой реализации можно вести параллельно. Главные неизвестные текущего этапа — детали ещё не опубликованной реализации и качество физического tracking наших virtual-legs reference. Проект следует принимать по этим промежуточным результатам.

### Как оценивать результат

Для первого эксперимента предлагается зафиксировать до обучения отдельные метрики:

| Уровень | Метрики |
|---|---|
| Данные | Доля действительных кадров, рассогласование времени, пропуски, frame/calibration consistency |
| Retargeting | Ошибка body/reference, FK/joint limits, residual опоры; для манипуляции — запястья и геометрия заданного захвата относительно предмета |
| Физика | Успешные захват/перенос/отпускание, object drops, падения, скольжение контактной точки стопы |
| Управление | Прогресс по маршруту, XY/yaw lag, ошибка верхней части тела, восстановление после потери наблюдения |
| Quest | Задержка, deadlines, RTF, температура/память на длительном прогоне |

Пороговые значения выбираются по геометрии конкретной сцены и фиксируются до сравнения. Например, успех чашки должен включать подъём, перенос в заданную область и устойчивое отпускание без скрытого weld. Достижение конца записи само по себе не заменяет этот критерий.

Сравнение вести на одинаковых reference и начальных условиях, нескольких training/evaluation seeds; записать новые сессии для независимой оценки. Не считать зеркала независимыми демонстрациями. Для virtual legs оценивать и фактическую походку: reference-based детектор trips может ошибаться, когда робот делает допустимый корректирующий шаг.

## 12. Что проект получит, а что останется исследованием

| Цель | Вердикт |
|---|---|
| Использовать идеи DexWeave в FURRY | **Да**, архитектурно совместимо с нашим направлением |
| Сегодня подключить авторский код/веса | **Нет**, в проверенном публичном релизе их нет |
| Обучать на наших Quest-записях | **Да**, начать с существующих body/virtual-legs эпизодов и проверки reference |
| Использовать virtual legs как основу | **Да**, это основной источник ног для обучения и исполнения |
| Сохранить автономный Quest и C++ | **Да по архитектуре**, производительность требует измерения |
| Сохранить текущие кисти и Grip | **Да**, заданный захват в текущем этапе; полная hand-policy отложена |
| Получить произвольное live teleop из одной reference-policy | **Не подтверждено**, потребуется отдельная программа обучения/проверки |
| Гарантировать авторское качество походки/захвата | **Пока нельзя**, отсутствуют воспроизведение и приёмка на наших данных |

**Предлагаемое решение для команды:** начать с имеющихся записей Meta virtual legs, согласовать reference и проверить физическое исполнение тела, сохранив Quest как целевой runtime. Затем добавить манипуляцию через запястья/Grip и заданную форму захвата. Решение о переходе с TWIST2 на новую политику принимать после сравнения; полную авторскую dexterous-постановку рассматривать отдельным расширением.
